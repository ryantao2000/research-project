## 创建计划前

仅在新研究问题、新实验执行范围或需要独立管理的实质交付出现时建立计划。普通阅读答疑、局部文档修正、已有授权内的必要修复，不自动建立计划。研究计划可以包含本轮取数、绘图和报告附录；独立跨计划报告生产才考虑单独立项。

先看本索引中相关计划，再读其 Results 和直接相关证据，判断已有设计、数据、基线、脚本是否可复用。只读必要材料，不要求通读所有计划、代码或日志。建立计划本身不等于获准执行实验。

研究问题、信息边界和已批准范围不变时，可在原计划追加阶段。问题改变则另立计划；只因旧计划较长或阶段结束，不自动另开编号。明确完成的计划不会因为尚有预算或证据限制而自动重启。

## 创建与编号

1. 新计划使用 `NN_slug.md`，编号全局唯一且不复用。检查现有计划及相关历史决定，不能仅按文件数量分配编号；`00_INDEX.md` 是入口，不是计划00。
2. 按需使用 `../../.claude/skills/research-project/templates/subplan.md`，同时建立同号同名 Results，初始注明尚未执行；没有发生的结果不预填。
3. 在本索引加入计划、问题、关系和 Results 链接。状态与预算保存在计划正文，总盘面负责摘要。
4. 采用中文正文，时间标明实际时区。计划下实验使用 `NN-M_slug`，run 身份和训练规模沿用项目规则。

## 计划写到什么程度

按工作类型选择内容，不凑固定章节或阶段数量。所有计划都应明确问题或交付目标、依据、范围、完成与停止条件、执行授权，以及必要资源。

实验计划另外写清：输入与评分单位、模型可见信息、控制变量、适当的强基线与负对照、主指标及不确定性、数据划分、失败标准和证据产物。一个受控比较说明唯一干预；多因素设计明确各因素与可归因边界，不把联合协议变化说成单因素因果。

阅读整理、教学和报告计划写清材料覆盖、来源保留、交付格式和核查方法，不硬套训练seed、GPU预算、负对照或模型指标。完成材料不等于用户读懂。

关键依赖区分实际核验、来源报告和待验证假设。说明假设不成立会影响什么、何时验证；未知机制可留在 Results 或分析正文，不强制建立另一套证据缺口台账。复用产物注明身份、位置及口径兼容性。

## 授权与资源

授权记录以每份计划正文为准。默认未授权的新实验先完成具体设计和资源估算，再请求一次批准；用户已明确授权的范围如实登记，不因补模板再次询问。授权时间、原话和范围必须有依据，不能补造。

授权块应包含：

- 授权状态与范围：哪些阶段、代码、检查、分析和交付物；部分授权逐项说明。
- 资源上限：按实际需要列计划累计与单run上限、并发、GPU卡时、CPU或本地计算、存储、费用。失败、重试、预检、推理与已占用资源计入相应预算；免费额度也有资源成本。
- 本地提交：在申请中明确是否包含本计划必要变更的选择性本地 Git 提交，及涉及哪些仓库。用户批准明确包含该项的计划后，无需跑前重复问；未包含则不能推定授权。
- 远程执行：需要时明确计算环境、代码传输范围、运行与产物回传。实验环境的代码传输不等于对外发布。
- 外部动作：push、对外上传、分享、发布或新服务，只有明确包含或另有明确授权才执行。
- 授权时间、原话及必要的修订依据。

批准后在范围和资源上限内连续完成，不在canary、Phase切换或批准范围内的恢复之间重复审批。触及预算、改变问题或数据/信息范围、引入未授权服务、需要修改受保护产物时停止相应动作；能独立进行的已授权工作可继续。澄清真正影响结果的信息不等于重复审批。

预算是上限，不是必须消耗的目标。达到完成标准就停止，不自动增加seed、对照或训练。旧计划以当时授权为准，新规则不追溯扩大旧授权。

## 从授权到结果

1. 建实验 `03_experiments/NN-M_slug/`，含 `00_INDEX.md`、`ENV.yaml`、`INPUTS.md` 和临时 `scratch/`。跑前写清：验证什么、唯一变量或设计因素、什么结果算失败。
2. 做与风险相关的preflight：环境/import、输入合同、必要单元测试和泄漏检查。涉及模型或模拟器时相关方法测试必须通过；依赖和相关实现未变，不重复全量审计。检查的实际资源开销纳入预算，不笼统称零成本。
3. 正式运行前按授权保存相关代码提交；独立代码仓库与工作区分别记录。不得夹带无关改动或重写历史。运行版本与必要的脏差异留证据，不能让已提交SHA掩盖实际执行的未提交改动。
4. runner 在计算前生成并冻结 `RUN_SPEC.json`，记录配置、代码仓库/版本、时间和上限。正式spec不手写；版本必须能在指定仓库唯一解析，不能只看SHA字符串长度。
5. 从启动起记录过程账：run_id、动作、偏离、失败与恢复、验证、资源和产物位置。runner按unit落盘，能识别完成部分；同一run首次读写前取得原子、非阻塞单进程锁，一个run只有一个supervisor。
6. 中断或失败保留现场和 `FAILED_RUN.json`。恢复另起run，记录 `resumed_from`、断点校验和、已完成量和已花费。并行run各自隔离可变状态，资源按总和计算。
7. 验证通过才能创建 `COMPLETE`；科学接纳另看协议与证据。accepted run只读，不覆盖。指标长表写前检查唯一键，额外信息参考独立命名且不参与公平排名。
8. 补 Results 的实际完成、方法构造、结果解释、成本对账、未执行项及证据限制；有科学主张才登记 CLAIMS，失败与负结果同样记录。报告或教学计划不伪造新的技术结论。

审读run按 `RUN_SPEC.json` → 验证摘要 → 进度守恒 → 指标及不确定性 → Results 核对；完成标记不能单独证明研究有效。临时scratch不作为结论证据。

复现第三方工作时，上游材料只读，适配代码放实验或方法开发位置；记录原样与适配的区别。逐项对照写入 `03_results/`，判定为对上、方向一致数值有差、对不上或无法验证，不调参数凑作者数字。

## 修订、暂停和完成

待执行设计可以根据用户讨论更新；改变设计的内容写回计划，解释性问答留实际问答记录。已经执行的阶段设计保留原样，通过追加修订记录说明后续变化。

追加阶段要同时检查研究问题、授权动作与剩余预算；不能只因为没超预算就自动扩大工作。方向改变或研究线关闭在计划中说明，并在决策日志留下跨计划决定。

完成时对照本计划交付物逐项说明：完成、未执行、失败或受外部条件限制。工程检查、科学结论、用户审阅和阅读掌握分别表述。仍有机制未知不自动使已完成计划变成未完成。

真正需要用户决定的事项写在配对 Results 的下一步部分，使用下面格式；批准后更新真实事项，旧决定及原话保留在计划修订记录：

```text
待你确认：具体要决定的动作、范围与代价
```

示例不是待办。本索引人工维护，project.py仅检查本地链接与目录配对，不汇总待办或产生授权。只读任务发现规则或索引问题时报告；已授权编辑任务可修正直接受影响的文档，不以维护为由扩大任务。
